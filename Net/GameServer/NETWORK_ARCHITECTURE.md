# 网络架构（新客户端协议）

## 当前数据路径

```text
客户端输入 / AI 模拟
    ├─ 业务指令 ──> SessionCommandQueue（每连接顺序、容量上限）──> 房间 / 存储
    └─ 位置等实时状态 ──> 直接校验 ──> 房间广播 ──> 每连接最新状态发送队列
                                                        └─ WebSocket ──> 客户端预测与平滑
```

通常情况下业务指令不再阻塞接收循环。版本与延迟探测也直接响应。登录、切图、对象生成销毁等指令构成顺序屏障：屏障期间丢弃位置状态，其他实时事件排在屏障之后。业务队列达到硬上限时，对必须执行的世界状态指令施加接收背压，避免静默丢失生成或切图；这时延迟探测也可能受阻，应视为过载信号。

每个位置快照必须包含 `roomId`、`sceneEpoch` 和对象 `sequence`。服务端检查房间、场景代次、控制权和序号后才保存与转发。切换地图时即使房间 ID 不变，场景代次也会增加。AI 位置始终批量转发，房间非玩家对象的生成消息内含初始快照；客户端和服务端须同步发布。

晚加入房间时，非玩家对象按最多 32 个一包发送生成与初始位置；动画和同步变量按约 48 KiB 分包发送。客户端在异步加载预制体期间按对象缓存最新位置、动画、同步变量及有序 RPC，加载完成后恢复。服务端在快照结束时补发期间已销毁对象的销毁消息，并在切图或离房后停止继续发送旧场景快照。怪物箱以最多 8 个并发生成请求代替逐只等待公网往返；服务端按房间原子维护 AI 控制者负载，不再每生成一只就扫描全部怪物。详细生成日志需启用 `NETWORK_SPAWN_TRACE` 才会编译进客户端。

右上角 `Ping` 是客户端请求到处理回包的完整耗时；`Srv A+Bms` 分别是服务端上一条已发送消息的队列等待与 WebSocket 写入时间，`Q客户端/服务端` 是探测时的待发送包数量。它们能指示服务端排队，但不能单独测出网络单程耗时或 Unity 主线程调度时间。

## 参考框架的具体借鉴

- [ET Actor/Mailbox](https://github.com/egametang/ET/blob/master/Book/5.4Actor%20Model.md)：同一实体的消息保持明确的顺序。当前先用每连接业务队列处理登录、切图与生成；服务器接管 AI 模拟时，应进一步改为每房间单写入的状态执行者。
- [Mirror Snapshot Interpolation](https://mirror-networking.gitbook.io/docs/manual/components/network-transform/snapshot-interpolation)：远端位置按发送时间进入固定容量缓冲，再按时间插值；短时缺包才按速度预测。缓冲倍率当前从 1.5 个发送周期开始，以较低显示延迟换取适度抗抖动，需在微信真机上按实际 Pos 与画面调节。
- [Mirror Timestamp Batching](https://mirror-networking.gitbook.io/docs/manual/general/timestamp-batching) 与 [Interest Management](https://mirror-networking.gitbook.io/docs/manual/interest-management)：现有 AI 消息已按对象批量处理；下一步要对怪物与玩家建立视野集合，在生成/销毁与位置广播中使用同一份集合，避免只过滤位置造成远处对象冻结。

游戏房间 AOI 需要先把怪物初始化 RPC 变成可重放的持久生成状态（目前 `InitMonster`/`InitBoss` 只在最初生成时广播）。直接过滤远处怪物生成包，会让之后进入视野的客户端缺少初始化，不能只改位置广播。服务端固定步长 AI 是下一项独立迁移：当前 Unity 客户端仍运行寻路、移动和战斗，不能仅靠网络队列替换。

## 权威边界与下一阶段

目前服务端权威管理房间、对象 ID 和控制权；玩家与 AI 的移动仍由有控制权的客户端模拟，服务端负责校验来源与转发。这个模型无法仅靠调插值彻底解决多人怪物同步，也无法证明客户端上报的位置符合物理和战斗规则。

下一阶段应把 AI 的寻路、移动与战斗状态移到服务器固定步长模拟。客户端上传玩家输入，服务器发布对象快照；客户端只做本地玩家预测、服务器校正和远端插值。先迁移一个怪物类型形成完整链路，再迁移其他怪物与战斗逻辑。微信小游戏端在 WebSocket 方案下仍受 TCP 排队影响；如需真正的可丢包传输，要单独设计微信 UDP 接入、认证及回退。

## 验证

自动检查覆盖队列顺序、容量、房间屏障、分片、批量权限和迟到快照。发布前需用微信真机测试单人及多人房间，分别记录 Ping、Pos、FPS、Q 和服务端发送队列日志；本地编译与模拟检查不能代表真实公网延迟。
