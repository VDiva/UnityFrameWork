# 独立 .NET 服务端同步优化

继续使用现有 ASP.NET Core + WebSocket 服务端。没有引入 Netick、Unity Dedicated Server，也没有修改 protobuf 或客户端 API。

## 本轮实现

- 实时状态按每连接的发送窗口合并，默认目标频率 30 Hz。同一窗口内不同对象都能发送；并非每个包都等待一个间隔。
- 可靠消息会唤醒窗口等待，先放行前面的状态，再按 FIFO 发送控制消息。生成、销毁、切图、RPC 等屏障仍然保留，状态不能跨越这些消息合并。
- AI 批量 Transform 使用共享的不可变载荷，积压时直接按对象 ID 合并状态。真正发送前才编码 protobuf；过期和被覆盖的快照不必先编码。多个接收者共享同一份最终编码结果。
- 大厅的 40 米可见范围使用空间网格粗筛，再检查精确三维距离、逻辑服务器和会话状态。候选同时包含旧可见对象，因此跨格、瞬移也会移除旧观察者。离房和断线时清理索引。
- 房间广播热路径直接枚举 ConcurrentDictionary，避免每次读取 Values 时复制整个成员集合。

这是对状态复制调度、编码和兴趣筛选的优化，不是完整的固定 Tick 游戏模拟、客户端预测或服务器回滚。游戏房间仍按现有成员关系同步，大厅可见范围保持原来的 40 米。

## 配置

通过 ASP.NET Core 配置项 `Networking:RealtimeSendRate` 设置，也可以使用 Linux 环境变量：

```sh
export Networking__RealtimeSendRate=30
```

允许 5～120；设置为 0 可关闭发送限频，恢复即时发送。默认值是 30。配置在服务启动时读取，每个新连接固定其发送间隔。30 Hz 在队列空闲且没有可靠消息时，会为实时状态增加最多约 34 毫秒的主动等待；高负载下实际延迟仍受调度和网络积压影响。

控制消息不承担这个主动等待。原有位置包过期丢弃、队列上限、发送超时和慢连接隔离继续生效。

## 验证

- 服务端 Debug 编译通过。
- `Tests/ServerReplicationChecks`：发送窗口、延迟编码、可靠屏障、共享编码、空间候选、离房重进、跨服隔离和断线清理。
- `Tests/SendQueueChecks`：既有 FIFO、超时、拥塞、慢客户端隔离和业务指令屏障。
- `Tests/RealtimeHotPathChecks`：实际会话处理、AI 批量同步、序列过滤、后加入状态及控制权转移。
- `Tests/RoomJoinabilityChecks`：房间加入、匹配、准备和切图等现有规则。

上述 WebSocket 检查使用可控的 WebSocket 替身，执行真实服务端处理和 protobuf 编解码；不是线上网络压测。没有测量或承诺实际部署中的 CPU、带宽或延迟降幅。


## 状态边界及房间索引（第二轮）

- 每个对象最多缓存 256 个 SyncVar，序列化数据累计最多 256 KiB，单值仍为 64 KiB。达到上限拒绝新增或超预算更新，原有状态保留，已有字段仍可在预算内更新。
- 玩家和房间对象按动画轨道缓存最新序号，最多 32 个轨道（0–31），动画名称最多 256 字符。玩家进入视野及晚加入恢复所有轨道；会话重置清空全部轨道，AI 转移权限清空旧轨道序号。
- 位置更新、子节点和初始生成共享有限数校验；最多 128 个子节点。启用的缩放、速度以及发送时间也进行校验。这是数据有效性检查，不替代业务移动速度及范围判定。
- 房间对象维护按房间索引，加入同步、所有者离开、AI 计数和清房只遍历目标房间；增删及索引快照在同一锁下完成，空房间索引及时回收。
- 下线用户在队列中等待 2 秒重连宽限期，按入队时间计算剩余等待；批量断线共享等待窗口，只有实际保存阶段占用 16 个并发名额。PendingCount 可观察待处理人数。队列仍保留不丢弃存档的无界语义。

验证使用 ServerReplicationChecks、RealtimeHotPathChecks、RoomJoinabilityChecks、SendQueueChecks 及 EquipmentRollChecks；这些是可控套接字/逻辑检查，尚未测量真实网络及数据库负载下的性能收益。


## 高频消息编码与初始状态打包（第三轮）

- 玩家单对象位置、玩家/房间对象动画、房间单对象位置现在使用 DeferredMessagePacket；队列先合并、判断过期，再进行首次编码。所有接收者通过线程安全 Lazy 共享同一字节数组。位置保留 250ms 过期策略，可靠消息顺序屏障不变。
- SyncVar 初始状态使用客户端已有 NetworkObjectStateBatch 协议，按约 48 KiB 预算拆包（合法的单字段可达 64 KiB，此时单独发包）。发送前等待快照队列容量并复核房间及场景 epoch，避免初始状态大量发包挤满发送队列。
- SyncVar 缓存记录字段序列化长度，替换时不再反复计算旧状态大小；初始发送只读缓存已有的私有快照，不再逐字段克隆。
- 受控测试结果：100 条积压的真实单对象 Protobuf 状态只编码最后 1 条；32 个并发读取者共享同一编码引用；101 个小型初始字段合为 1 个包，3 个 32 KiB 字段拆成 3 包且数据完整。
- 无协议文件或 Unity 客户端依赖变更；实际带宽及 CPU 收益取决于观察者数量、消息大小和积压程度，尚未进行真实网络压测。
